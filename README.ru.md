# Contract-Driven Development

**Три фазы, три артефакта. Рабочий процесс для пары «человек + AI-агент», где узкое горлышко — не скорость агента, а время человека на проверку.**

## Проблема

Агент генерирует что угодно за секунды. Стандартный паттерн — «план → утверждение → исполнение» — ломается на шаге «утверждение». Агент пишет план на 1000 строк. Вы читаете, думаете «бля, всё не то», и час жизни уходит.

**Корень проблемы**: читать чужой текст трудно. Отвечать на конкретный вопрос — легко.

## Решение

Агент не пишет вам. Агент спрашивает вас. Вы отвечаете коротко. Агент работает автономно в заданных границах.

```
Фаза 0: Анализ        → агент читает задачу и изучает код (молча)
Фаза 1: Контракт      → адаптивные вопросы → 20 строк YAML
Фаза 2: Карта         → 200–300 слов, проверка направления
Фаза 3: Имплементация → слайсы, авто-продолжение на зелёных тестах
```

Вы касаетесь процесса три раза:
1. Ответили на вопросы, которые агент не смог вывести из кода (1–2 минуты)
2. Глянули карту, сказали «ок» (15 секунд)
3. Заглянули на красный слайс (редко)

## С чем работает

Один файл — все harness-ы. Скопируйте `SKILL.md` в нужное место:

| Harness | Куда положить | Как вызвать |
|---------|--------------|------------|
| **Claude Code** | `.claude/commands/contract.md` | `/contract` |
| **Hermes Agent** | `~/.hermes/skills/software-development/contract-driven-development/SKILL.md` | `skill_view(name='contract-driven-development')` |
| **Cursor** | `.cursor/rules/contract-driven.md` | Загружается автоматически |
| **OpenCode** | `.opencode/skills/contract-driven.md` | Загружается автоматически |
| **Aider** | `.aider/commands/contract.md` | `/contract` |

Контракты сохраняются в `.hermes/contracts/`, `.claude/contracts/` или туда, куда пишет артефакты конкретный harness — путь настраивается в самом скилле.

YAML-контракт — портабельный артефакт. Даже если вы смените harness посреди проекта, контракт останется валидным.

## Фаза 0: Анализ (молча)

Перед любыми вопросами агент читает задачу и изучает релевантный код. По каждому измерению контракта проверяет: это можно вывести из кодовой базы? Если да — заполняет сам и не спрашивает. Если нет — добавляет вопрос в Фазу 1.

## Фаза 1: Контракт

Агент не пишет план. Агент задаёт только те вопросы, которые Фаза 0 не смогла закрыть — без фиксированного числа, без ритуальных вопросов. Есть 5 измерений контракта:

| Измерение | Вопрос | Поле в контракте |
|-----------|--------|-----------------|
| Границы | Что нельзя трогать? | `boundaries` |
| Инварианты | Что должно остаться правдой? | `invariants` |
| Приёмка | Как поймём что готово? | `acceptance` |
| Стиль | Какие библиотеки/паттерны использовать? | `style` |
| Контекст | Что случилось и почему сейчас? | `context` |

Вопросы, на которые агент может ответить из кода, пропускаются. Если все измерения понятны из контекста — агент сразу показывает черновик контракта.

На выходе — YAML на 20–30 строк. Человек утверждает контракт, а не план.

## Фаза 2: Карта

Агент по контракту рисует карту. 200–300 слов. Twitter-формат:

```
Map: Добавить экспорт отчётов в CSV

Files:
  src/export/csv.go        — modify: add ExportToCSV method
  src/handlers/reports.go  — modify: add GET /reports/export
  tests/export_test.go     — new: 12 test cases

Flow:
  HTTP GET → handler → CSV builder → file download

Tests:
  unit: ExportToCSV edge cases (empty, unicode, large)
  integration: handler returns 200 + valid CSV

Order:
  1. ExportToCSV method
  2. Handler endpoint
  3. Tests
```

Человек проверяет одно: правильное ли направление?

**Карта — это гипотеза, а не обещание.** Новые файлы, обнаруженные в процессе реализации, добавляются молча — без остановки, без повторного согласования — если они не в `boundaries`. Карта «неверна» только если меняется сам подход, а не когда нашёлся лишний файл.

## Фаза 3: Имплементация с чекпоинтами

Агент режет работу на атомарные слайсы (одно глагольное словосочетание, компилируется сам, одна тестовая цель). После каждого слайса:

```
Слайс → тесты → зелёные?            → авто-продолжение
                    ↓ нет
            TDD-красный (ожидаемый)? → авто-продолжение к слайсу реализации
                    ↓ нет
            Регрессионный красный
                    ↓
            Агент диагностирует причину
                    ↓
            Стоп-карточка → человек выбирает А / Б / В
                    ↓
            Агент исполняет → продолжение
```

Формат стоп-карточки:
```
STOP — Regression: <имя теста>

Problem:  <что упало>
Cause:    <что в этом слайсе это вызвало>
Fix:      <предложенный фикс>

Next:
  A) Применить предложенный фикс → продолжить
  B) Откатить слайс N, попробовать иначе: <альтернатива>
  C) Уточнить контракт: <какое допущение оказалось неверным>
```

Человек вмешивается только при регрессии или когда агент упёрся в решение, не покрытое контрактом.

## Почему это работает

| Обычный подход | Contract-Driven |
|---|---|
| Агент пишет план (легко) | Агент задаёт вопросы (легко) |
| Человек читает план (тяжело) | Человек отвечает на вопросы (легко) |
| Агент исполняет (легко) | Агент исполняет в рамках контракта (легко) |

Асимметрия развёрнута в пользу человека.

## Ближайшие аналоги

- **Shape Up (Basecamp)**: pitch → scope → build. Компактные документы, явные границы.
- **TDD**: тесты как контракт, red-green-refactor как чекпоинты.
- **Dependabot/Renovate**: авто-мёрж на зелёном CI, человек вмешивается только на красном.

Contract-Driven Development собирает эти идеи в агентный воркфлоу.
